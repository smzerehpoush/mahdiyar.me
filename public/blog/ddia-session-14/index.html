The Unix philosophy

Small tools, one interface, composed.

Top 5 most-called endpoints, in one line.

cat access.log |
  awk '{print $7}' |      # take the URL field
  sort             |      # bring identical URLs together
  uniq -c          |      # count each run
  sort -rn         |      # most frequent first
  head -n 5

Do one thing well

Each program is small, and they combine in ways no one planned.

Uniform interface

Everything reads and writes lines of text on stdin and stdout.

Easy to experiment

Inputs are never modified, so you can rerun and inspect each stage.

sort spills to disk when data exceeds memory, so this pipeline handles logs far larger than RAM. An in-memory hash table would be faster for small data but fails on big data. The limitation of Unix tools: they run on one machine. MapReduce is Unix tools distributed across thousands.
02

MapReduce

Unix pipes across a thousand machines.

Lab: one MapReduce job

Count payments per status. Each line is one input record.
1. Map: emit (key, 1)
2. Shuffle: sort and group by key
3. Reduce: sum per key

Input lives in a distributed filesystem (HDFS). Mappers run where the data is. The framework sorts and moves data between them: the shuffle.

You write only map and reduce; partitioning, sorting, moving data, and retrying failed tasks are the framework’s job. Real workflows chain dozens of jobs, scheduled by tools like Airflow, Oozie, Azkaban, or Luigi.

Joins without random lookups.

Sort-merge join: key both inputs by the join key. The shuffle delivers each merchant’s record and all its events to the same reducer.

No network round trip per record. Hot keys? Spread them over several reducers.

Map-side joins avoid the shuffle when you know more about the inputs: broadcast hash join (one side is small enough to fit in memory on every mapper), partitioned hash join (both inputs partitioned the same way), and map-side merge join (both already sorted). Querying a remote database per record would be slow and would overload it.

Batch outputs, and why they’re safe.

Build indexes and stores

Search indexes, or whole key-value database files built in bulk and swapped in atomically.

Immutable inputs

A buggy job can be fixed and rerun. Old output can be kept for rollback.

Retry is safe

Failed tasks rerun on another machine; partial output is discarded.

Human fault tolerance: bad code doesn’t destroy data, it just produces output you can throw away.

Compare with an online database, where a bad deploy can corrupt records permanently. Hadoop also embraced storing raw data first and deciding how to interpret it later (the “sushi principle”: raw is better), and designed for frequent task kills, since Google ran batch jobs at low priority and preempted them often.

Beyond MapReduce

Fewer disk writes, smarter plans.

Dataflow engines: Spark, Flink, Tez.

Dataflow engines

On top: declarative APIs (Spark DataFrames, Hive, Pig) with query optimisers. Graph jobs use Pregel-style message passing.

Recomputing from lineage only works if operators are deterministic. Hash-map iteration order and random numbers without fixed seeds are classic sources of non-determinism.
