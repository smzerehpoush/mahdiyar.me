Relational vs document

A fifty-year-old debate, rerun with new names.

Every challenger got hype. SQL stayed.

Why NoSQL? More scale and write throughput, open source, specialised queries, and frustration with rigid schemas.
Relational databases were born in 1960s–70s business data processing: transactions and batch jobs. They generalised remarkably well to almost everything on the web. NoSQL was originally just a catchy hashtag for a 2009 meetup on open-source distributed non-relational databases; later reinterpreted as "Not Only SQL". The likely future: relational alongside a variety of non-relational stores — polyglot persistence.

The object-relational (impedance) mismatch: objects in code vs rows and columns in tables. ORMs like Hibernate — what we use through JPA — cut the boilerplate but can't fully hide the difference. For self-contained, tree-shaped data like a résumé, a JSON document matches the object shape and has better locality: one query, one place. But watch the third readout when you toggle.

Store "ir:21", not "Greater Tehran".

Anything meaningful to humans may need to change someday. An ID never does.

Removing duplicated human-meaningful data is the whole idea of normalisation.

Consistent spelling No ambiguity between same-named cities Rename once, updated everywhere Easy to localise Smarter search (city → province)
Storing text duplicates the meaningful info in every record: renames mean updating every copy, with write overhead and inconsistency risk. But normalising requires many-to-one relationships (many people in one region), which don't fit the document model well. In relational DBs, referencing by ID is normal because joins are easy. Document DBs often have weak join support, so the join moves into application code.

Data grows more connected with every feature.

Companies become entities with pages and logos. Users recommend each other. Suddenly the tree has many-to-many links.

No joins in the database? Then your application code does them.

Even if version 1 of your app fits a join-free document model, data tends to become more interconnected. The book's examples: organisations and schools as first-class entities (with their own pages), and recommendations that must show the recommender's current photo — both need references, which need joins when queried.

We’ve had this argument before.

Hierarchical · IMS, 1968

A tree of nested records, like JSON. Great for one-to-many. No joins: duplicate data or chase references by hand.

Network · CODASYL

Records with many parents, linked by pointers. Queries walk access paths by hand. Change the paths, rewrite the code.

Relational · SQL

Everything laid out in the open. The query optimizer picks the access path. New index? Queries use it automatically.

Build the optimizer once, and every application benefits. The general solution wins in the long run.

IMS was built for stock-keeping in the Apollo program and is still maintained. Its problems in the '70s look a lot like document-DB problems today. CODASYL generalised the tree to allow many parents; programmers had to track access paths in their heads — the committee itself compared it to navigating an n-dimensional space. The relational model won because the optimizer makes access-path decisions automatically. Document DBs went back to nesting for one-to-many, but for many-to-one/many-to-many they use IDs (document references) just like foreign keys — they have not followed CODASYL.

So which one leads to simpler code?

Document wins when…

  • data is a tree of one-to-many
  • you load the whole tree at once
  • records are heterogeneous
  • you want schema flexibility

Shredding a tree into many tables makes schemas and code clumsy.

Relational wins when…

  • you need joins
  • many-to-one references are common
  • many-to-many relationships appear
  • all records share a structure

Denormalising or app-side joins push complexity into your code.

You can't say in general which model gives simpler code; it depends on the relationships between data items. A document limitation: you can't refer directly to a nested item — you say "the second position of user 42", like an access path. Fine if nesting is shallow. Poor join support may not matter at all, e.g. an analytics event log.

“Schemaless” is a myth. It’s schema-on-read.

Your reading code still assumes a structure. The only question is who enforces it: the database at write time, or your code at read time. Like static vs dynamic typing.

Schema-on-read: handle old shapes in code 
if (user.fullName != null && user.firstName == null) {
  // written before the split
  user.firstName = user.fullName.split(" ")[0];
}
Schema-on-write: migrate (PostgreSQL) 
ALTER TABLE users ADD COLUMN first_name text;
UPDATE users
   SET first_name = split_part(full_name, ' ', 1);
ALTER TABLE ADD COLUMN takes milliseconds in most databases (MySQL historically copied the whole table). The UPDATE rewriting every row is the slow part on a big table — you can leave the column NULL and fill it in at read time, exactly like the document approach. Schema-on-read shines when data is heterogeneous: many object types, or structure dictated by external systems you don't control. When all records share a structure, an explicit schema documents and enforces it. Chapter 4 goes deeper into schema evolution.

Locality: a win only if you read the whole thing.

A document is stored as one blob. Reading one field still loads it all; growing it usually means rewriting it all.

Keep documents small.

Locality isn't document-only: Google Spanner can interleave child rows inside a parent table; Oracle has multi-table index cluster tables; Bigtable's column families (Cassandra, HBase) manage locality. Only in-place updates that don't change the encoded size are cheap for documents. More on locality in Chapter 3.

The two models are converging.

JSON in SQL
PostgreSQL (since 9.3), MySQL, DB2 can store, index, and query inside documents.
Joins in NoSQL
RethinkDB joins; some MongoDB drivers resolve references client-side.
1970
Codd’s original paper already allowed nested relations as values.

A hybrid of relational and document is a good route for databases to take.

For us: PostgreSQL's jsonb gives document-style storage with indexing (GIN) inside the same transactional database. Codd called nested values "nonsimple domains" — JSON-like trees inside a relation, 30+ years before SQL got JSON support.
02

Query languages

Say what you want, not how to get it.

Imperative says how. Declarative says what.

Imperative 
List<Payment> failed = new ArrayList<>();
for (Payment p : payments) {
  if (p.status() == FAILED) {
    failed.add(p);
  }
}
Declarative 
SELECT * FROM payments
WHERE status = 'FAILED';
Concise
Easier to write and read.
Free to optimise
No promised order, so the DB can reorganise storage and pick indexes.
Parallel
A pattern, not an algorithm: easy to spread across cores and machines.
SQL follows relational algebra closely. Key insight: the imperative loop implicitly relies on list order; the database can't know whether your code depends on it, so it can't move records around safely. SQL guarantees no order unless you ask, so the engine can compact, reorder, and add indexes without breaking queries. Being more limited is what gives the optimiser room. CPUs now get faster by adding cores — declarative queries parallelise; ordered instructions don't.

Lab: CSS is declarative too

User clicks:
Declarative: li.selected > p { background: yellow }
Imperative: loop over DOM, set style

Click “Run JS once”, then select a different page.

The CSS rule declares a pattern; the browser keeps it true as the page changes and can optimise how it matches. The imperative version sets a style once and goes stale when the selection moves — and to use a faster API you'd have to rewrite it. Same lesson as SQL vs IMS/CODASYL's imperative COBOL record-at-a-time loops.

MapReduce: somewhere in between.

Refunded amount per month, three ways:

Moral: NoSQL systems tend to reinvent SQL, in disguise.

MapReduce (Google, more in Chapter 10) was offered by MongoDB and CouchDB for read-only queries. map and reduce must be pure: no extra DB queries, no side effects — so the DB can run them anywhere, in any order, and retry on failure. Writing two coordinated functions is harder than one query and gives the optimiser less room, so MongoDB 2.2 added the declarative aggregation pipeline — roughly a subset of SQL in JSON syntax.

Graph-like models

For when anything can relate to anything.

Vertices and edges.

Social
people → who knows whom
Web
pages → links, ranked by PageRank
Roads
junctions → roads, shortest path

Vertices don’t have to be one kind. Facebook keeps people, places, events, check-ins, and comments in one graph.

Property graph in two PostgreSQL tables 
CREATE TABLE vertices (id bigint PRIMARY KEY, props jsonb);
CREATE TABLE edges (
  id bigint PRIMARY KEY,
  tail bigint REFERENCES vertices, -- from
  head bigint REFERENCES vertices, -- to
  label text, props jsonb);
CREATE INDEX ON edges (tail); CREATE INDEX ON edges (head);
Why it’s flexible
  • Any vertex can link to any other
  • Traverse forward and backward (two indexes)
  • Labels keep many relationship kinds in one clean model
  • Easy to extend as features grow
Property graph model (Neo4j, Titan, InfiniteGraph): each vertex has an id, outgoing and incoming edges, and properties. Each edge has an id, tail vertex, head vertex, a label, and properties. Graphs handle things a rigid relational schema struggles with: different regional structures per country, varying granularity (a city for one person, a province for another).
