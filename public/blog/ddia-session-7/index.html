01

Multi-leader

Every datacenter, device, or editor is a leader.

When does it make sense?

Several datacenters

A leader per region: local write latency, and a region can fail or lose its link without stopping writes elsewhere.

Offline clients

A calendar app on your phone accepts edits offline. Every device is effectively its own datacenter.

Collaborative editing

Google Docs style: each user’s local copy accepts edits and syncs later.

Often bolted on after the fact, and it interacts badly with auto-increment keys, triggers, and constraints. Avoid it if you can.

Within one datacenter, multi-leader rarely pays off. CouchDB was designed for the offline case. Collaborative editors either take a lock (effectively single leader) or merge concurrent edits.

Write conflicts arrive late.

With a single leader, the second write would have waited or failed. Making conflict detection synchronous would remove the main benefit of multi-leader.

Resolving conflicts.

Avoid them

Route all writes for one record to the same leader, e.g. the user’s home region. The most common recommendation.

Converge

Last write wins by timestamp or ID (simple, loses data), or merge values, or keep both and let code or a human decide.

Merge automatically

CRDTs, mergeable data structures, operational transformation (used by collaborative editors).

Custom resolution code can run on write (when the replication log sees a conflict) or on read (all versions are returned to the app). In all-to-all topologies, writes can arrive out of order — an update before the insert it depends on — so leaders need version vectors to order them. Circular and star topologies break if one node fails.
02

Leaderless

Write to several replicas. Read from several. Vote.

Dynamo-style replication.

The client (or a coordinator) sends every write to all n replicas and waits for w acks. Reads ask r replicas and take the newest version.

Read repair

A read that sees a stale replica writes the new value back to it.

Anti-entropy

A background process compares replicas and copies missing data.

No failover needed: if a node is down, writes simply go to the others. Read repair works well for frequently read values; anti-entropy catches rarely read ones, without ordering guarantees.

Run it several times with n=5, w=3, r=3: the read always overlaps the write. Then set w=2, r=2: sometimes you read stale data. A common choice is n odd (3 or 5), w = r = (n+1)/2.

Even with w + r > n, edge cases leak.

  • A sloppy quorum writes to stand-in nodes during an outage (hinted handoff), so the overlap guarantee is gone.
  • Two concurrent writes: which one wins isn’t clear, and last-write-wins by clock can drop one.
  • A write concurrent with a read may or may not be seen.
  • A write that reached fewer than w nodes is reported as failed but is not rolled back.
  • A node holding the new value fails and is restored from an older one.

Quorums give probabilities, not guarantees. Monitoring staleness is also harder than measuring a follower’s lag.

Dynamo-style databases are built for use cases that tolerate eventual consistency. For stronger guarantees you need transactions or consensus (sessions 9–13).
03

Concurrent writes

“Concurrent” has nothing to do with clocks.

Capturing happens-before with versions.

Two operations are concurrent if neither knew about the other, regardless of wall-clock time. With multiple replicas, a single version number becomes a version vector: one counter per replica. Last-write-wins (Cassandra’s only option) drops concurrent writes silently; it’s only safe if each key is written once, e.g. with UUID keys.
