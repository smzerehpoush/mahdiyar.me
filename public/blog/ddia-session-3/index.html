The world’s simplest database: two shell functions.

kv_set () {
  printf '%s,%s\n' "$1" "$2" >> store.log
}

kv_get () {
  grep "^$1," store.log | tail -n 1 | cut -d, -f2-
}
O(1)
writes: just append to a file
O(n)
reads: scan everything

Fix the reads with an index: extra structure derived from the data. Every index speeds reads and slows writes.

Appending to a file is about the fastest write possible, and many real databases use an append-only log internally. Reads are terrible. An index helps reads but must be updated on every write — which is why databases make you choose indexes explicitly instead of indexing everything.
01

Log-structured engines

Only ever append. Clean up later.

Hash index: remember where each key lives.

Keep an in-memory hash map from each key to its byte offset in the log. One seek per read.

Split the log into segments; compact and merge them in the background.

Great for

Lots of writes per key, all keys fit in RAM. Example: a play counter per video.

Weak at

Too many keys for memory. Range queries: each key must be looked up separately.

This is roughly what Bitcask (Riak’s default engine) does. Practical details: binary format with length prefixes, deletion via a tombstone record, crash recovery by snapshotting the hash map, checksums to catch partially written records, and a single writer thread.

–

Set a key a few times, then Get it, then Compact.

Each Set appends; the stale entries fade out. Compaction throws away everything except the newest value per key. Why append instead of overwrite? Sequential writes are much faster, crash recovery is simpler (no half-overwritten values), and the file never fragments.

SSTables: keep each segment sorted by key.

Sorting buys three things: merging segments is simple and efficient even if they exceed memory; the in-memory index can be sparse (one key every few KB, then scan); and blocks between sparse keys can be compressed. Compaction strategies: size-tiered (Cassandra, HBase) and leveled (LevelDB, RocksDB). Lucene’s term dictionary uses the same idea.
02

B-trees

The default for 50 years: fixed pages, updated in place.

Pages pointing to pages.

4 KB
fixed-size pages, read and written one at a time
~500
child references per page (branching factor)
256 TB
fits in just four levels at that branching factor
Look up 251: follow the reference whose range contains it, down to a leaf. A page split happens when a leaf is full; the tree stays balanced with O(log n) depth. Updates overwrite pages in place, so crash safety needs a write-ahead log (redo log), and concurrency needs latches. Optimisations: copy-on-write pages (LMDB), abbreviated keys in interior pages, sibling pointers for range scans.

LSM vs B-tree: no universal winner.

LSM-treeB-tree
Writes✓ usually faster, sequential✕ each write hits WAL + page
Reads✕ may check several segments✓ one path down the tree
Disk usage✓ compresses well, less fragmentation✕ pages partly empty after splits
Latency tail✕ compaction can stall requests✓ more predictable
Transactions✕ a key can live in many segments✓ each key in exactly one place

Write amplification: one logical write turning into many physical writes. On SSDs it eats both throughput and lifespan.

Rules of thumb only — benchmark with your own workload. A big risk with LSM engines at high write rates: compaction falls behind, segments pile up, reads slow down, disk fills. You need to monitor it explicitly.
03

Other indexes

Secondary, clustered, multi-dimensional, fuzzy, in-memory.

Beyond the primary key.

Secondary index

Keys aren’t unique: store a list of row IDs, or make keys unique by appending the row ID.

Heap vs clustered

A heap file holds rows and indexes point at it (PostgreSQL). A clustered index stores the row inside the index (MySQL InnoDB primary key).

Covering index

Stores some extra columns in the index so certain queries never touch the table (INCLUDE in PostgreSQL).

Multi-column

Concatenated keys, or R-trees for things like latitude and longitude (PostGIS).

Fuzzy

Full-text search engines like Lucene can match misspellings within an edit distance.

In-memory

Redis, VoltDB: fast mainly because they skip encoding data for disk, not because they skip disk reads.

Updating a row in a heap file in place works if the new value isn’t larger; otherwise it moves and indexes need updating. In-memory databases still get durability via logs, snapshots, or replication.
