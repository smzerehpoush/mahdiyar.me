Analytic queries are usually written by analysts and feed business intelligence. Running them on the OLTP database hurts the latency of user-facing transactions — which is why warehouses exist.
01

Data warehousing

A separate database, built for questions.

Extract, transform, load.

Copy data out of every OLTP system into one read-only database, shaped for analysis. Analysts can query freely without slowing the business down.

TeradataVerticaRedshiftSAP HANAHiveSpark SQLPresto / TrinoImpala

Star schema: one huge fact table, many small dimensions.

Facts are events: each payment is a row, often with 100+ columns.

Dimensions answer who, what, where, when, how: merchant, method, date, region.

A snowflake schema normalises dimensions further.

Even the date is a dimension, so you can encode things like public holidays and filter on them. Snowflakes are more normalised; stars are simpler for analysts.
02

Column-oriented storage

Read only the columns you need.

Store each column on its own.

A fact table can have hundreds of columns, but a typical query touches four or five. In a row store you still read every column of every row. In a column store each column lives in its own file, and row k is the k-th entry in every file.

Try the aggregate queries in both layouts, then the point lookup. Column stores win big on scans of few columns; row stores win on fetching whole rows. Note: Cassandra and HBase "column families" are still row-oriented storage — different idea despite the name.

Columns compress beautifully.

country column: DE DE DE FR FR NL NL NL NL DE DE FR
DE bitmap: 111000000110  →  runs: 0, 3, 6, 2, 1
FR bitmap: 000110000001  →  runs: 3, 2, 6, 1
NL bitmap: 000001111000  →  runs: 5, 4, 3

WHERE country IN ('DE','NL') = bitwise OR of two bitmaps. AND across columns = bitwise AND.

Few distinct values per column → one bitmap per value → long runs of zeros → run-length encoding. Then the CPU chews through compressed chunks in its cache using SIMD: vectorised processing.

Bitmap encoding works well when distinct values are few compared to rows. Column-compressed data also fits better in memory and CPU caches; the bottleneck shifts from disk bandwidth to memory bandwidth and CPU.

Sort order and writes.

Pick a sort key

Sort whole rows by e.g. date, then merchant. Date-range queries skip most data, and the first sort column compresses into a handful of runs.

Several sort orders

Replicas can store data in different orders, so different queries each find a helpful one (C-Store, Vertica).

Writes go LSM-style

Inserting into the middle of sorted compressed columns is painful. Buffer writes in memory, then merge into new column files in bulk.

Unlike multiple secondary indexes in a row store, each sort order stores the full data, not pointers. Queries combine the on-disk column files with the in-memory buffer transparently.
03

Precomputed aggregates

Do the work once, read many times.

Materialised views and data cubes.

A materialised view stores the query result. A virtual view is just a saved query.

A data cube precomputes totals across combinations of dimensions, e.g. revenue by date × merchant.

Upside

Some queries become instant reads.

Downside

Less flexible: you can only slice by dimensions you precomputed. Updates on write cost extra.

Warehouses keep raw data as much as possible and use cubes only as a speed-up for common queries.
