Why transactions exist.

Disks fail, processes crash mid-write, networks drop, clients race each other. A transaction groups reads and writes into one unit that either commits or aborts.

If it aborts, the application can safely retry. Whole classes of partial failure disappear.

Crash halfway throughTwo clients overwrite each otherReading half-finished dataLost connection mid-commit
Transactions are not a law of nature; some NoSQL systems dropped them for scale. They’re a trade-off, not a given.
01

The meaning of ACID

Marketing term, specific guarantees.

Four letters, unevenly useful.

Atomicity

Really abortability: on error, all the transaction’s writes are discarded. Nothing to do with concurrency.

Consistency

Your application’s invariants, like credits equal debits. The database can’t know them, so this one is really yours.

Isolation

Concurrent transactions don’t step on each other. Formally: serializable. In practice often weaker.

Durability

Committed data isn’t forgotten: written to disk and/or replicated. There is no perfect durability.

The C was arguably added to make the acronym work. BASE (basically available, soft state, eventual consistency) is even vaguer. Oracle’s “serializable” is actually snapshot isolation.

Retrying aborted transactions isn’t free.

  • The transaction committed, but the network dropped the acknowledgement. A retry runs it twice unless you deduplicate.
  • The error was overload. Retrying makes it worse: back off and limit retries.
  • The error is permanent, like a constraint violation. Retrying is pointless.
  • The transaction had side effects outside the database, like sending an email or calling a bank.
  • The client itself crashes while retrying, and the data is lost.
Single-object atomic operations (atomic increment, compare-and-set) are useful but are not transactions in the usual sense. Multi-object transactions are needed for foreign keys, denormalised counters, and secondary indexes staying in sync.
02

Weak isolation

What “read committed” and “repeatable read” actually promise.

Read committed: no dirty reads, no dirty writes.

Default in PostgreSQL, Oracle, SQL Server. Writes take row locks; reads see the last committed version.

Dirty writes: two transactions overwrite each other’s uncommitted data; row-level locks prevent this. Holding read locks would let a long writer block all readers, so databases keep the old committed value around instead.

Read skew: a snapshot fixes it.

Snapshot isolation matters for backups, long analytic queries, and integrity checks. Implemented with MVCC: each row version is tagged with the transaction that created and deleted it, and visibility rules decide which version a transaction sees. PostgreSQL calls it repeatable read; the SQL standard’s names are muddled.

Lost updates: the read-modify-write trap.

Other fixes: automatic lost-update detection (PostgreSQL repeatable read aborts one of the transactions; MySQL InnoDB does not), and compare-and-set: UPDATE … WHERE balance = old_value, or a version column. JPA’s @Version is exactly compare-and-set.

Write skew: two correct decisions, one broken rule.

Pattern: SELECT checks a condition → app decides → write changes the condition. Double bookings, duplicate usernames, double spending.

When the write doesn’t touch rows that the check read — or the check looked for rows that don’t exist yet (a phantom) — row locks can’t help. Options: serializable isolation, explicit FOR UPDATE on the rows the check depends on, or materialising conflicts into lockable rows. Next session covers serializability.
