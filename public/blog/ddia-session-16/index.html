01

Reasoning about time

Event time is not processing time.

When did it happen, and when did we hear about it?

A phone queues events offline and sends them hours later. A consumer restarts and works through a backlog. Grouping by processing time gives nonsense.

Group by event time, and decide what to do with stragglers: ignore them, or publish a correction.

Three timestamps

When it happened (device clock), when it was sent (device clock), when it was received (server clock). The last two estimate the device’s clock offset.

You can never be sure a window is complete, since a delayed event might still arrive. Track the number of dropped late events as a metric.

02

Stream joins

Joins that never finish.

Three kinds of stream join.

Stream–stream

Match a search with clicks on its results within one hour. Keep recent events of both sides as state.

Stream–table

Enrich each payment with merchant details. Keep a local copy of the table, updated through change data capture.

Table–table

Maintain a materialised view, like the Twitter home timeline cache from session 1.

The catch: if the joined data changes over time, which version applies? The fee rate at the time of the payment, not today’s.

This is called a slowly changing dimension. A common fix is to give each version of a record its own ID, so the join is deterministic, at the cost of keeping all versions.

Fault tolerance

Exactly once, effectively.

Crash between “done” and “recorded as done”.

“Exactly-once” really means effectively-once: the visible outcome is as if each event was processed once, though some processing may have repeated internally. Side effects outside the framework (emails, HTTP calls) still need their own idempotency.
