Chapter 4.

Old and new versions always overlap.

Servers roll out node by node. Mobile users don’t update for months. Stored data outlives the code that wrote it.

Backward compatible

New code can read data written by old code. Usually easy: you know the old format.

Forward compatible

Old code can read data written by new code. Harder: it must ignore what it doesn’t understand.
Rolling upgrades are what make deploys without downtime possible, and they guarantee a period where versions mix.
01

Formats

From Java serialisation to Avro.

Formats to avoid, and formats to use carefully.

Language built-ins

Java Serializable, Python pickle: locked to one language, slow, poor versioning, and decoding can instantiate arbitrary classes, a classic security hole.

JSON, XML, CSV

Human-readable and everywhere. But: numbers are ambiguous (IDs above 253 break in JavaScript), no binary strings (Base64 adds 33%), schemas are optional.

Binary JSON variants

MessagePack, BSON: a bit smaller, but field names still repeat in every record.

Twitter returns tweet IDs twice in its API, once as a number and once as a string, because JavaScript parsers lose precision above 2^53. JSON/XML are still fine for data exchange between organisations: agreeing on any format is the hard part.

Same record, how many bytes?

JSON (minified)81 B
MessagePack66 B
Thrift Binary59 B
Thrift Compact34 B
Protocol Buffers33 B
Avro32 B

The binary schema-based formats drop field names entirely. They store a tag number (Thrift, Protobuf) or nothing at all (Avro).

These numbers are the book’s measurements for one small example record. The exact sizes matter less than the pattern: once field names leave the payload, records shrink by more than half.

Two schema philosophies.

Protocol Buffers: tags identify fields
message Settlement {
  required int64  id          = 1;
  optional string merchant    = 2;
  repeated string fee_codes   = 3;
}
Avro IDL: no tags at all
record Settlement {
  long          id;
  union { null, string } merchant = null;
  array<string> feeCodes;
}

Protobuf / Thrift

Each field has a tag number in the bytes. Code generation from the schema.

Avro

Bytes are just values in schema order. Decoding needs the writer’s schema, resolved against the reader’s schema.

How an Avro reader knows the writer’s schema: in a large file, put it once in the header; in a database, store a schema version number per record and keep a registry; over a network connection, negotiate it once. Avro shines for dynamically generated schemas such as dumping a database table.
02

Schema evolution

Which changes are safe?

Lab: will this change break anything?

Backward compatible: new code reads old data
Forward compatible: old code reads new data

Rules of thumb: only add fields that are optional or have defaults; only remove fields that are optional or have defaults; never reuse a Protobuf tag number. Forward compatibility is what lets old services keep running during a rolling deploy.

Schemas are worth it.

Smaller
no field names in every record
Documented
the schema is always up to date, unlike docs
Checked
compatibility can be tested before you deploy

Plus code generation for statically typed languages like Java.

03

Modes of dataflow

Through databases, services, and messages.

Through a database: data outlives code.

This is a real risk with ORMs that map a whole row or document into a class and save it all back. Within a database you may have data written years ago; migrating it all is optional and expensive, so most databases fill new columns with null when old rows are read.

Through services: RPC isn’t a local call.

Location transparency (making remote calls look local) is fundamentally flawed. REST embraces the network; modern RPC frameworks (gRPC, Finagle) are more explicit about it. For public APIs you can’t force clients to upgrade, so you keep old versions working, often for a very long time.

Through messages: send it and move on.

Buffer

The broker absorbs bursts and outages of the consumer.

Redeliver

Messages to a crashed process can be delivered again.

Decouple

The sender doesn’t need the receiver’s address, and one message can reach many consumers.

Actor frameworks (Akka, Orleans, Erlang) pass messages too, so the same forward/backward compatibility rules apply during rolling upgrades.
