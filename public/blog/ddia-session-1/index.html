Glue code makes you a data system designer.

Put a cache and a search index next to your database, and keeping them in sync is now your job.

The categories are blurring: Redis is a datastore that can act as a queue; Kafka is a queue with database-like durability. Once we combine tools behind an API, we've built a new special-purpose data system and must uphold its guarantees ourselves — e.g. that the cache is correctly invalidated. Whoever writes the invalidation logic is designing a consistency guarantee.

Three words we use daily and rarely define.

01

Reliability

Continuing to work correctly, even when things go wrong.

A fault is not a failure.

Fault: one component breaks its spec.
Failure: users stop getting service.

Faults will happen. The job is to stop them becoming failures.

A fault is one component deviating from its spec; a failure is the system as a whole no longer providing service. You can't make fault probability zero, and you can't tolerate every fault (the book's example: Earth swallowed by a black hole). So we tolerate specific kinds of faults. Example: a DB replica going down is a fault; if users see errors, it became a failure. Exception: security — where no cure exists, prevention wins.

Where faults come from

~1/day
Hardware. Disk failures in a 10,000-disk cluster. Random, mostly independent.
1 second
Software. The 2012 leap second hung many services at once. Bugs are correlated across nodes.
#1
Humans. Operator config errors led outages in one study; hardware played a role in only 10–25%.
Hardware: MTTF of disks is 10–50 years, so at scale failures are daily. Old fix: redundancy (RAID, dual PSUs). Modern fix: tolerate losing whole machines in software — which also enables rolling upgrades. Software: systematic faults like a bug triggered by one bad input on every node, runaway processes, slow dependencies, cascading failures. They're usually environment assumptions that were always true until they weren't. Humans: configuration errors were the top cause in a study of large internet services.

Break things on purpose.

Many critical bugs hide in error handling. Netflix’s Chaos Monkey randomly kills processes so the recovery path is always tested.

Designing for unreliable humans

APIs that make the right thing easy Sandboxes with real data Tests at every level Fast rollback Gradual rollouts Tools to recompute data Detailed telemetry
Deliberately inducing faults keeps fault-tolerance machinery exercised. For human error: minimise opportunities for error (but don't over-restrict or people work around it), decouple where mistakes happen from where they cause damage, test thoroughly, make recovery quick, monitor clearly. A system can also check its own guarantees while running and alert on discrepancies.

02

Scalability

Not a label. A question about growth.

“Our system is scalable.”

“If load grows like this, what are our options?”

First describe today’s load with a few load parameters:

requests / secread : write ratioconcurrent userscache hit ratea few extreme cases
Saying "X is scalable" or "Y doesn't scale" is meaningless. Scalability means asking: if the system grows in a particular way, what are our options; and how do we add resources to handle extra load? Which load parameters matter depends on the architecture. Sometimes the average matters, sometimes the bottleneck is a small number of extreme cases.

Twitter, 2012: the problem was fan-out.

tweets / sec
300k
timeline reads / sec
30M

Posting averages 4.6k requests/sec (12k at peak) — easy on its own. Home timeline reads are ~300k/sec. The hard part: each user follows many people and is followed by many. One tweet has to reach every follower's timeline.

Work at read time, or at write time?

1. Join when reading

One global tweets table. Each timeline read runs:

SELECT tweets.*, users.* FROM tweets
JOIN users   ON tweets.sender_id = users.id
JOIN follows ON follows.followee_id = users.id
WHERE follows.follower_id = :me

Couldn’t keep up with 300k reads/sec.

2. Fan out when writing

A cached “mailbox” per user. Each tweet is pushed into every follower’s timeline.

Reads become cheap, and reads outnumber posts ~100×.

But 4.6k tweets × 75 followers = 345k writes/sec, and one celebrity tweet = 30M writes.

Final answer: a hybrid. Fan out for most users; merge celebrities in at read time.

The key load parameter for Twitter is the distribution of followers per user (weighted by tweet frequency), not tweet volume. The read-time vs write-time trade-off recurs throughout the book: indexes, materialized views, and Chapter 12 revisits this exact example.

Response time is a distribution, not a number.

GC pausecontext switchlost packet + TCP retransmitpage faultrack vibration (really)
Batch systems care about throughput; online systems care about response time. Latency and response time are often used interchangeably but differ: response time includes network and queueing delays; latency is the time a request waits to be handled. Even an identical repeated request varies — the chips are the book's examples of random added latency. For a Java team: when did we last look at GC logs?

Optimising p99.99 was deemed too expensive for Amazon — diminishing returns. Head-of-line blocking: a server processes few things in parallel, so slow requests hold up the queue, and the client sees slow responses even for fast requests. Load testing: the load generator must keep sending regardless of responses, or queues stay artificially short.

Tail latency amplification: parallel backend calls mean the user waits for the slowest. With 1% slow calls and 100 calls per request, about 63% of user requests are slow. The probability slider moves in 0.1% steps.

Never average percentiles.

To combine servers or time windows, add the histograms, then read the percentile.

HdrHistogramt-digestforward decayMicrometer percentile histograms
For dashboards: keep a rolling window (e.g. 10 minutes) and compute percentiles each minute. Sorting all values works but is costly; approximation algorithms like t-digest and HdrHistogram are cheap. Question for the team: do our dashboards show averages or percentiles, and how are they aggregated across instances?

No magic scaling sauce.

Real systems mix both. Stateless services spread easily; a stateful database doesn’t.

100k × 1 kB / s
vs
3 × 2 GB / min

Same throughput. Completely different systems.

Expect to rethink architecture at every order-of-magnitude growth. Scale up = bigger machine; scale out = shared-nothing across many machines. Elastic scaling helps with unpredictable load; manual scaling is simpler. Common wisdom: keep the database on one node until cost or availability forces distribution. Scalable architectures are built on assumptions about which operations are common; wrong assumptions waste effort. For unproven products, iteration speed beats hypothetical scale.
03

Maintainability

Most of the cost of software comes after launch.

Bug fixes, operations, investigating failures, platform migrations, new use cases, tech debt. Every legacy system is unpleasant in its own way; the goal is to avoid creating new ones.

Operability

Make it easy for ops to keep it healthy.

Monitoring, automation, no single-machine dependency, predictable behaviour, good defaults you can override.

Simplicity

Make it easy for a new engineer to understand.

Remove accidental complexity: the kind that comes from the implementation, not the problem.

Evolvability

Make change easy when requirements shift.

Agility, but at the level of the whole data system, not just the code.

Best weapon against complexity: good abstractions. SQL hides disk layouts, concurrency, and crash recovery.

Operability: good ops can work around bad software, but good software can't run reliably with bad ops. Simplicity: symptoms of complexity include state-space explosion, tight coupling, inconsistent naming, performance hacks, special cases ("big ball of mud"). Moseley and Marks define accidental complexity as not inherent in the user's problem. Evolvability: requirements change constantly — business priorities, regulation, platforms, growth.
